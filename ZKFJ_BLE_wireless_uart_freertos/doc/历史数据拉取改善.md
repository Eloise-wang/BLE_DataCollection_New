# 历史数据拉取丢帧问题分析与改善方案

> 修订日期：2026-06-01
>
> 适用范围：ZKFJ BLE DataCollection 下位机固件 + 上位机应用层

---

## 一、问题根因分析

### 1.1 丢帧现象

- 43200 条记录（24h × 2s 间隔），理论字节数：43200 × 18 = 777,600 字节
- 实测第一次仅收到 34,498 条，第二次 37,151 条，第三次 38,281 条
- 随拉取次数增加，收到数量递增，说明问题**不是存储层写坏**，而是**传输层丢帧**

### 1.2 丢帧根因定位

根据对 `proto_cmd_handler.c` 中 `proto_handle_request_history` 的分析，当前实现在收到 0x04 请求后：

1. **立即连续发送**所有数据帧（`while (offset < total_bytes)` 循环）
2. 每帧之间仅 `vTaskDelay(pdMS_TO_TICKS(5U))` = **5ms 间隔**
3. BLE Controller 的 TX 缓冲区（通常 4~8 包）在 BLE 5.0 2M PHY 高速发送下会迅速积满
4. 一旦缓冲区满，后续帧被 BLE Controller 丢弃（这是 BLE HCI 层行为，应用层感知不到）
5. 5ms 间隔在 BLE 连接不稳定（信号衰减、重传）或链路带宽争用时完全不够

**根本问题**：下位机以"流"的方式不间断发送，上位机无任何反馈机制（没有 flow control / stop-and-wait），当 BLE 链路出现瞬时拥塞时，数据丢失无法恢复。

### 1.3 数据帧 offset 机制回顾

当前数据帧格式中每帧携带：

- `offset`：本帧数据在文件中的**起始字节位置**（小端 u32）
- `total_bytes`：文件总字节数（同一 task_id 下所有帧相同）

这意味着**每帧的 offset 是全局唯一的字节位置**，上位机可以检测 offset 是否连续来判断丢帧。

## 二、方案评审

### 2.1 方案优势

"突发模式（Burst）+ 精确续传"思路**完全正确**，有以下优点：

1. **引入 flow control**：下位机发 N 帧后停下来，上位机有时间处理
2. **减少往返次数**：从 3535 次往返（严格停等）降至 ~71 次（burst=50）
3. **天然支持断点续传**：offset 字段已有，上位机记录已确认字节位置即可
4. **丢帧可检测可恢复**：offset 跳跃时从断点重传

### 2.2 方案细节说明

通信示意图：

```
上位机: GET[offset=0, count=50]           GET[offset=11000, count=50]
            ↓                                     ↓
下位机:  DATA[0~10999] (50帧)          DATA[11000~21999] (50帧)
```

- `offset` 的单位是**字节**，`count` 是请求的**帧数**
- 50 帧 × 220 字节/帧 = 11000 字节/批，所以第二次请求的 offset=11000
- `count` 表示请求的帧数（1~255），offset 始终以字节为单位

### 2.3 配套改进点


| 改进点               | 说明                                           |
| ----------------- | -------------------------------------------- |
| **每帧数据最大 220 字节** | BLE MTU 247 下取 220 作为安全余量，帧数约 3535           |
| **动态帧间隔**         | 根据突发窗口大小调整间隔（窗口大时增大间隔，给 BLE Controller 缓冲时间） |
| **突发窗口上限 50 帧**   | 平衡效率与可靠性，防止一次发太多导致缓冲区积压                      |
| **重传保护**          | 上位机连续 3 次重传失败后记录警告，不无限重试                     |

## 三、协议详细设计

### 3.1 请求帧格式（Host → Device）

**命令帧格式 SOF=0xA5：**

```
┌────────┬──────────────┬────────────────────┬──────────────┬────────────┐
│ CMD    │ task_id      │ offset              │ count        │ file_sel   │
│ 1字节   │ 8字节 LE    │ 4字节 LE            │ 2字节 LE    │ 1字节      │
└────────┴──────────────┴────────────────────┴──────────────┴────────────┘
```

- `CMD` = 0x04（历史数据请求）
- `task_id` = 任务 ID（64 位 LE）
- `offset` = 请求从第几个**字节**开始（0 = 从头开始）
- `count` = 请求的**帧数**（1~255，建议 50）
- `file_sel` = 文件区选择：
  - `0x00` = Data 区（主数据）
  - `0x01` = PreData 区（预采数据）
  - `0x02` = Meta 区（元数据）
  - `0x03` = Log 区（日志）

**payload 长度**：8 + 4 + 2 + 1 = 15 字节
**帧总长度**：1 (SOF) + 1 (CMD) + 1 (LEN) + 15 (PAYLOAD) + 2 (CRC16) = 20 字节

### 3.2 数据帧格式（Device → Host）

```
┌────────┬──────────┬──────────────┬──────────────────────┬──────────────────────────┬────────┐
│ SOF    │ len      │ task_id      │ offset               │ total_bytes              │ data   │ CRC16 │
│ 1字节   │ 2字节LE │ 8字节LE     │ 4字节LE              │ 4字节LE                  │ N字节   │ 2字节LE│
└────────┴──────────┴──────────────┴──────────────────────┴──────────────────────────┴────────┴────────┘
```

### 3.3 ACK 帧格式（Device → Host）

```
┌────────┬──────────┐
│ SOF    │ status   │
│ 1字节   │ 1字节    │
└────────┴──────────┘
```

- `SOF` = 0xA5
- `status`：
  - `0x00` = OK
  - `0x01` = 任务未找到
  - `0x02` = 参数错误
  - `0x03` = 存储错误

## 四、下位机实现要点

### 4.1 核心处理函数

直接替换原 `proto_handle_request_history` 函数。payload 长度检查改为 15 字节，移除无限循环，改为突发窗口循环：

```c
void proto_handle_request_history(const proto_cmd_msg_t *msg)
{
    /* 参数解析 */
    if (msg->len < 15U)
    {
        proto_send_ack(msg->cmd, PROTO_STATUS_LEN_ERROR);
        return;
    }

    uint64_t task_id;
    uint32_t offset;
    uint16_t count;
    uint8_t  file_sel;

    (void)proto_payload_read_u64_le(&msg->payload[0],  msg->len, &task_id);
    (void)proto_payload_read_u32_le(&msg->payload[8],  msg->len - 8U, &offset);
    (void)proto_payload_read_u16_le(&msg->payload[12], msg->len - 12U, &count);
    file_sel = msg->payload[14];

    /* 获取总字节数 */
    uint32_t total_bytes = 0U;
    switch (file_sel)
    {
        case 0U: (void)APP_Storage_GetDataSize(task_id, &total_bytes); break;
        case 1U: (void)APP_Storage_GetPreDataSize(task_id, &total_bytes); break;
        case 2U: (void)APP_Storage_GetMetaSize(task_id, &total_bytes); break;
        case 3U: (void)APP_Storage_GetLogSize(task_id, &total_bytes); break;
        default: proto_send_ack(msg->cmd, PROTO_STATUS_PARAM_ERROR); return;
    }

    /* 参数校验 */
    if (total_bytes == 0U)         { proto_send_ack(msg->cmd, PROTO_STATUS_NOT_FOUND);     return; }
    if (offset >= total_bytes)      { proto_send_ack(msg->cmd, PROTO_STATUS_PARAM_ERROR);   return; }
    if (count == 0U)               { proto_send_ack(msg->cmd, PROTO_STATUS_PARAM_ERROR);   return; }

    /* 限制 count 上限，防止一次发太多帧导致 BLE 缓冲区满 */
    if (count > 50U) count = 50U;

    /* BLE 流控：帧间隔根据窗口大小动态调整 */
    uint32_t frame_delay_ms = (count <= 10U) ? 3U : (count <= 30U) ? 5U : 8U;

    /* 发 ACK */
    proto_send_ack(msg->cmd, PROTO_STATUS_OK);

    TASK_SetHistorySending(true);

    uint32_t pos = offset;
    uint16_t frames_sent = 0U;

    /* BLE MTU=247，payload 最大 PROTO_MAX_CHUNK_SIZE 字节 */
    uint8_t data_buf[PROTO_MAX_CHUNK_SIZE];
    uint8_t frame_buf[1 + 2 + 8 + 4 + 4 + PROTO_MAX_CHUNK_SIZE + 2];

    while (frames_sent < count && pos < total_bytes)
    {
        uint16_t to_read = (uint16_t)((total_bytes - pos < (uint32_t)PROTO_MAX_CHUNK_SIZE)
                                      ? (total_bytes - pos)
                                      : (uint32_t)PROTO_MAX_CHUNK_SIZE);

        int nread = -1;
        switch (file_sel)
        {
            case 0U: nread = APP_Storage_ReadData(task_id, pos, data_buf, to_read); break;
            case 1U: nread = APP_Storage_ReadPreData(task_id, pos, data_buf, to_read); break;
            case 2U: nread = APP_Storage_ReadMeta(task_id, pos, data_buf, to_read); break;
            case 3U: nread = APP_Storage_ReadLog(task_id, pos, data_buf, to_read); break;
            default: break;
        }
        if (nread <= 0) break;

        size_t out_len = 0U;
        if (!PROTO_DataBuildFrame(task_id, pos, total_bytes,
                                  data_buf, (uint16_t)nread,
                                  frame_buf, sizeof(frame_buf), &out_len))
        {
            break;
        }

        proto_send(frame_buf, out_len);
        pos += (uint32_t)nread;
        frames_sent++;

        /* 发满 count 帧后停下来，等上位机的下一个请求 */
        if (frames_sent >= count) break;

        /* BLE 流控间隔，给 Controller 刷新缓冲区的喘息时间 */
        vTaskDelay(pdMS_TO_TICKS(frame_delay_ms));

        /* BLE 断开时立即停止 */
        if (!s_ble_connected) break;
    }

    TASK_SetHistorySending(false);
}
```

| 突发窗口上限            | 50 帧 | 建议值，可配置            |

## 五、上位机实现要点

### 5.1 状态机设计

```
┌──────────────────────────────────────────────────────────────┐
│                      IDLE                                     │
│  收到用户"开始拉取" → 发送 GET[task_id, offset=0, count=50]  │
└─────────────────────┬────────────────────────────────────────┘
                      ↓
┌──────────────────────────────────────────────────────────────┐
│                      RECEIVING                                │
│  循环：                                                            │
│    - 收到数据帧 → CRC校验 → 检查offset是否连续                   │
│      · offset == expect → 缓存data，推进expect                  │
│      · offset > expect  → 丢帧！发送GET[expect, count=2]补漏    │
│      · offset < expect  → 重复帧，丢弃（防重传过度）            │
│    - 收到帧数 == count → 发送 GET[expect, count=50] 继续        │
│    - expect >= total_bytes → 完成，退出                        │
│  超时未收到帧 → 重发当前请求（最多3次）                         │
└─────────────────────┬────────────────────────────────────────┘
                      ↓
┌──────────────────────────────────────────────────────────────┐
│                      COMPLETE / ERROR                        │
│  全部数据已收 or 连接断开 or 超过最大重试次数                  │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 核心 Python/Pseudo-code 实现

```python
class HistoryPuller:
    def __init__(self, burst_count=50, max_retry=3):
        self.burst_count = burst_count      # 突发窗口大小（帧数）
        self.max_retry = max_retry          # 丢帧后最大重试次数
        self.offset = 0                     # 当前已确认的字节偏移
        self.received_bytes = bytearray()
        self.total_bytes = None

    def pull(self, task_id, file_sel=0):
        self.offset = 0
        self.received_bytes.clear()
        self.total_bytes = None
        self._send_get(task_id, 0, self.burst_count, file_sel)

        consecutive_empty = 0

        while True:
            frame = self._recv_frame()  # 阻塞接收（实现时设置合理超时）

            if frame is None:
                # 连接断开或超时
                if self.total_bytes is not None and self.offset >= self.total_bytes:
                    break  # 数据已全部发完，只是不小心超时
                consecutive_empty += 1
                if consecutive_empty >= self.max_retry:
                    print(f"[ERROR] 连续{self.max_retry}次未收到帧，退出")
                    break
                # 重新请求当前窗口
                self._send_get(task_id, self.offset, self.burst_count, file_sel)
                continue

            consecutive_empty = 0  # 收到帧，重置计数器

            # CRC 校验（从 len 第一个字节到 data 最后一个字节）
            if not self._check_crc(frame):
                print("[WARN] CRC校验失败，忽略该帧")
                continue

            frame_offset = frame["offset"]
            frame_data = frame["data"]

            if self.total_bytes is None:
                self.total_bytes = frame["total_bytes"]

            # 落在已收范围内的重复帧 → 忽略
            if frame_offset < self.offset:
                continue

            if frame_offset == self.offset:
                # 正常顺序帧：追加并推进
                self.received_bytes.extend(frame_data)
                self.offset += len(frame_data)

            elif frame_offset > self.offset:
                # 丢帧检测：offset 有跳跃
                gap_bytes = frame_offset - self.offset
                print(f"[WARN] 检测到丢帧 {gap_bytes} 字节 (offset跳跃: {self.offset} -> {frame_offset})，请求重传")
                # 先保存这帧（它可能在重传窗口内）
                self.received_bytes.extend(frame_data)
                self.offset = frame_offset + len(frame_data)
                # 从断点精确续传：只请求丢失的那部分
                self._send_get(task_id, frame_offset, self.burst_count, file_sel)
                continue

            # 当前突发窗口收满 → 发起下一个请求
            if self._should_send_next_request():
                self._send_get(task_id, self.offset, self.burst_count, file_sel)

            # 传输结束
            if self.offset >= self.total_bytes:
                print(f"[OK] 拉取完成，共 {len(self.received_bytes)} 字节")
                break

    def _should_send_next_request(self):
        # 当已收字节数达到一个窗口的量（burst_count × 平均帧数据大小）时请求下一批
        # 简化判断：offset 推进到了某个窗口边界
        WINDOW_SIZE = self.burst_count * 220  # ~11000 字节
        return (self.offset % WINDOW_SIZE == 0) and (self.offset > 0)

    def _send_get(self, task_id, offset, count, file_sel):
        """发送 GET 请求"""
        payload = struct.pack("<QIHB",
            task_id,   # Q = uint64_t LE
            offset,    # I = uint32_t LE
            count,     # H = uint16_t LE（1~255）
            file_sel,  # B = uint8_t
        )
        self._send_bytes(bytes([0x04]) + payload)

    def _check_crc(self, frame):
        """CRC16/MODBUS 校验：从 len 第一个字节到 data 最后一个字节"""
        raw = frame["raw"]
        crc_range = raw[1:-2]  # 去掉 SOF 和末尾 CRC
        calc_crc = self._calc_crc16(crc_range)
        rx_crc = int.from_bytes(raw[-2:], "little")
        return calc_crc == rx_crc

    def _calc_crc16(self, data: bytes) -> int:
        crc = 0xFFFF
        for b in data:
            crc ^= b
            for _ in range(8):
                crc = (crc >> 1) ^ 0xA001 if (crc & 1) else crc >> 1
        return crc
```

### 5.3 丢帧重传流程示例

```
场景：窗口大小 50 帧，期望 offset=8800（已收到第40帧）

第41帧到达：offset=9020 > 8800
  → 检测丢帧：丢失 offset=8800~9019（220字节 = 1帧）
  → 发 GET[offset=8800, count=2]  ← 从断点精确续传，仅请求丢失的1帧+下一帧
  → 收到 offset=8800（补帧）✅
  → 收到 offset=9020（继续）✅
  → 继续正常流程
  → 发 GET[offset=11000, count=50]
```

### 5.4 突发窗口大小建议


| 场景           | burst_count | 每批字节数  | 说明           |
| ------------ | ----------- | ------ | ------------ |
| 稳定环境（实验室）    | 100         | ~24KB  | 丢帧率极低，效率优先   |
| 一般环境（办公室）    | 50          | ~12KB  | 平衡效率与可靠性     |
| 恶劣环境（工厂/远距离） | 20          | ~5KB   | 丢帧率高，小窗口减少浪费 |
| 极不稳定（多设备干扰）  | 10          | ~2.4KB | 最小化单批丢帧影响    |


### 5.5 性能对比


| 模式           | 帧数（约）    | 往返次数   | 传输时间（理想） | 丢帧恢复     |
| ------------ | -------- | ------ | -------- | -------- |
| burst=10     | 3535     | 354    | ~27 秒    | 精确续传     |
| **burst=50** | **3535** | **71** | **~5 秒** | **精确续传** |
| burst=100    | 3535     | 36     | ~2.7 秒   | 精确续传     |


> 丢帧恢复一次额外开销约 75ms~150ms（1次往返），对总时间影响极小。

## 六、错误处理汇总

### 6.1 上位机


| 错误            | 处理方式                              |
| ------------- | --------------------------------- |
| CRC 校验失败      | 忽略该帧，等待重传                         |
| offset 跳跃（丢帧） | 发送 GET[offset=丢失位置, count=2] 精确续传 |
| 连续 N 次未收到帧    | 重发当前请求；超过 max_retry 后记录错误并退出      |
| 连接断开          | 重新连接后，从 last_ack_offset 继续        |


### 6.2 下位机


| 错误          | 处理方式                   |
| ----------- | ---------------------- |
| task_id 不存在 | ACK status=0x01        |
| offset 越界   | ACK status=0x02        |
| Flash 读取失败  | ACK status=0x03，停止发送   |
| BLE 断开      | 停止发送，退出函数，下次请求从头/从断点继续 |
